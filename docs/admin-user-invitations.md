# 管理画面からのメールログイン用ユーザー作成

## 利用フロー

1. 運営の管理者が Refine 管理画面の「ユーザー」→「ユーザーを作成」で表示名とメールアドレスを入力する。
2. アカウントを作成し、本人に初回パスワード設定メールを送る。
3. 本人がリンクを開き、パスワードと確認用パスワードを入力して設定する。
4. 設定完了後、通常のログイン画面でメールアドレスとパスワードを入力する。毎回のメール確認は従来どおり必要で、メールの「確認する」ボタンか、ログイン画面での6桁番号の入力で完了する。

作るのは一般のサービス利用ユーザーであり、`admin_users` の管理者ではない。
組織への所属やセッション作成権限は付与しない。作成権限は既存のユーザー詳細で別途設定する。
表示IDはメールアドレスと無関係なユーザーID由来の値を自動採番する。
生年月日・性別・住所の補助データは任意であり、アカウント作成時には作らない。既存の `GET /user` は未登録の補助データを空のレスポンスとして扱い、プロフィールを取得できる。読み取り時に空のDB行を追加しない。
既存のGoogle/LINEアカウントの統合やパスワード追加、設定済みパスワードのリセットは対象外。
メールの照合は既存のメールログインと同じHMAC・大文字小文字の扱いを保つ。

## API と認証

- `POST /v1/manage/users`: JSON `{ displayName, email }`。管理者Cookie認証と管理画面用Origin制限が必要。201 `{ userID, invitationSent }`。
- `POST /v1/manage/users/{userID}/invitation`: 初回設定が未完了のアカウントに再送。管理者専用。200 `{ userID, invitationSent }`。
- `POST /auth/password/setup`: JSON `{ token, password }`。初回設定用リンクの秘密値で認証する。成功204。ログインCookie・トークンは返さない。
- `GET /auth/password/policy`: 認証不要。新しいパスワードの制約 `{ minLength, maxBytes }` を返す。キャッシュしない。pepperやハッシュの値は返さない。
- 管理者用ユーザー情報の `passwordSetupRequired` は初回設定待ちかを示す。ユーザーJWTや `/users/me` には追加しない。

リンクは `WEBSITE_URL` のHTTPSオリジン + `/auth/password/setup#...`。
リクエストのHostからURLを組み立てない。メールとWebのデプロイ先が一致するよう設定する。
Webの設定ページは別リポジトリの対応が必要で、APIだけの先行公開では本人が設定を完了できない。
新規環境変数やAWSリソースは増やさず、development / productionは既存SES、localはループバックSMTPを利用する。

## 初回設定画面

Webは[Figmaの「新しいパスワードを設定」画面](https://www.figma.com/design/tv3ShpqHoVS79xGUJlSgKb?node-id=48-8061)を参考に、ログインと同じブランド背景・見出し・パスワード入力・ボタンを使用する。
入力欄の見出しは「新しいパスワード」「パスワード確認用」、確認用の説明と「完了」ボタンを流用する。
認証コードについての説明と8文字の条件は現在のフロー・実装と異なるため、初回設定の説明と12文字の条件に置き換える。
既存パスワードの変更・リセット処理や、その前段の認証コード画面はこの機能には追加しない。

## 安全性とエラー

- 設定完了まではパスワード認証情報・ログインセッションを作らず、メールは未確認にする。本人の初回設定時にメール確認済みになる。
- 32バイトの暗号学的乱数を用い、DBにはSHA-256ハッシュのみ保存する。24時間有効・一度だけ使用可能。
- URLのフラグメントはサーバーへのGETに送られない。Webは読み取り後にURLから削除し、解析スクリプトを読み込まず、`no-store` / `no-referrer`を設定する。
- リンクを開いただけでは設定もログインも行わない。メールクライアントのプレビュー等でリンクを消費しない。
- 再送は60秒間隔。再送すると古いリンクを無効化する。期限切れでも未完了アカウントは再送できる。
- パスワードは12文字以上。既存bcrypt方式を使うため、UTF-8バイト長とpepperの合計は72バイト以内。パスワードはトリミングしない。
- サーバーの `password_auth.PasswordPolicy.Validate` に制約判定を集約し、登録・初回設定・変更・ローカル作成CLIで共用する。ログインではこの新規設定用ルールを適用せず、既存の短いパスワードとの互換性を維持する。
- Webは上記APIから制約を取得し、Unicodeコードポイント数とUTF-8バイト数で検証する。取得に失敗した場合は固定値にフォールバックせず、入力と送信を無効にする。確認用パスワードとの一致はWebだけの入力補助で、サーバーは受け取ったパスワードを必ず再検証する。
- 管理画面の表示名は50コードポイント以内、メールは既存のメールログイン対応形式で254バイト以内。前後の空白を同じ扱いで除去する。HTMLのUTF-16文字数上限やブラウザ独自の検証に依存しない。
- ユーザー行を同一の順序でロックし、初回パスワード登録・メール確認・リンク消費を同一トランザクションで実行する。
- メール／subjectの変更、退会、既存パスワードの存在を確認し、既存の認証情報を上書きしない。
- 管理画面の同一メールでの作成は、メールsubjectに対するトランザクションロックで直列化する。既存の認証テーブルを一括変更・整理しない。
- 監査ログに管理者IDと対象ユーザーIDを記録する。メール、パスワード、リンク、配信エラーの生テキストは記録しない。

メールはDBコミット後に送信する。送信失敗でも作成済みアカウントを残し、`invitationSent: false`を返す。
管理画面は「作成済みだが送信できなかった」と表示し、詳細から再送できる。
タイムアウト等で配信結果が不明な場合も同じ扱いになる。永続outboxや自動リトライ、exactly-once配信は導入しない。

## テスト

`scripts/test-mail.sh` とCIで、既存メール認証と招待の単体・HTTP・実DBの競合テストを実行する。
DB統合テストは `MAIL_TEST_DATABASE_URL` に接続し、一時スキーマを作成・削除する。通常のユーザー行は変更しない。
プロフィール取得の回帰テストは `ADMIN_TEST_DATABASE_URL` を使い、テストデータをトランザクションのロールバックで破棄する。補助データの未登録・空・暗号化済み・暗号データの破損を区別し、プロフィール取得で不要な補助データを作成しないことを確認する。

検証対象: 管理者以外の拒否、Origin制限、入力不備、重複・同時作成、送信失敗、再送の間隔と旧リンク失効、期限切れ、再利用、設定・再送の競合、登録失敗のロールバック、退会・メール変更・既存パスワード、初回設定後のパスワード＋6桁番号ログイン。

Webの `PASSWORD_SETUP_TEST_API_URL=http://127.0.0.1:8082 pnpm test` は検証用ローカルAPIと制約の境界値を比較する。実際の招待リンクは使わず、アカウントを書き換えない。通常のテストではこの統合テストをスキップする。
