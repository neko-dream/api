# 管理画面のユーザー閲覧

運営の管理画面アカウントで、ことひろの一般ユーザーを閲覧する。管理画面アカウント自体の一覧（管理者メニュー）とは別の画面。

## 画面

- `/admin/users`: 表示名・表示ID・ユーザーIDによる部分一致検索、20件ずつのページ送り、メール・状態・登録日時の表示。
- `/admin/users/show/:id`: 基本情報、確認済みメールの状態、ログイン方法、登録・更新・退会日時の表示。
- 検索とページはURLに保持する。詳細へのリンクは内部ユーザーIDを使う。
- 一覧取得失敗と空一覧、詳細の404とサーバー障害を区別し、再試行できる。

## API

- GET `/v1/manage/users/list?offset=0&limit=20&search=...`
- GET `/v1/manage/users/{userID}`
- PUT `/v1/manage/users/{userID}/permissions`（`{"canCreateTalkSession": true/false}`）
- GET `/users/me`（一般ユーザーのCookie認証、基本プロフィールと現在有効な作成権限のみ）

既存の未実装一覧APIを実装し、レスポンスを `{users, totalCount}` に変更した。管理画面用OpenAPIとGoコードを再生成する。現在は登録日時降順・ユーザーID降順の固定順序で、未実装だった並び替えパラメーターは削除した。

既存のAdminCookieAuthを必須とする。一般ユーザーのSessionIdや組織への所属では認証されない。メールは既存Encryptorで復号する。復号失敗は既存ユーザー詳細と同じ方法で記録し、そのメールを非表示・未確認として他の項目の閲覧を続ける。暗号化メールに対する文字列検索は行わない。パスワードハッシュ・ソルト・OAuth subject・トークン・人口統計情報は返さない。

ユーザーの作成・プロフィール編集・削除は含まない。詳細画面で独立したセッション作成権限を許可・解除できる。組織への所属と既存セッションの編集権限は変わらない。ゲスト・退会済みユーザーには許可できない。

権限更新は対象状態の確認と書き込みをSQLで同時に実行する。コマンド側は表示用queryやメール復号に依存しない。成功・失敗の監査はusecaseから既存の構造化ログへ出力する（運営ユーザーID・対象ユーザーID・許可値。資格情報・メールは記録しない）。独立した監査テーブルは追加しない。

## 作成権限と移行

- migration 58で`users.can_create_talk_session`を追加する。新規ユーザーはfalse。既存の有効な非ゲスト組織メンバーへは、一度だけ許可を引き継ぐ。以後の組織加入・通常ログインでは自動付与しない。
- APIを先にデプロイしてmigrationを適用し、続けてWebの`/users/me`による判定を展開する。token/infoと組織コードログインは権限の取得先にしない。
- 退会中は許可が保存されていても作成できない。復帰時は元の許可を維持する。復帰後も禁止したい場合は運営が許可を解除する。
- downは許可列を削除するため手動許可・解除の履歴を失う。upの再適用はその時点の組織メンバーへ再付与する。運用中のロールバックでは許可を退避し、安易にdown/upしない。
- 許可解除は以後の権限確認に反映される。確認済みの実行中リクエストを強制キャンセルする仕様ではない。

## ローカル確認

運営アカウントで`/admin/users`へログインし、通常ユーザーの詳細を開いて「作成を許可」を実行する。通常ユーザーが`/make/new`を開いて作成できること、許可解除後に作成できなくなることを確認する。ローカル環境でも認可を免除しない。

E2Eは専用の使い捨てDBで実行する。既存シナリオにはテスト作成者だけへの明示的なSQL許可を追加している。通常ログインへの自動付与や実環境用の迂回エンドポイントは追加しない。

管理画面のビルド成果物はコミットしない。`server/static/admin-ui/index.html`はgo:embed用のプレースホルダーとして残し、デプロイ時の`pnpm build`で環境ごとの成果物を生成する。

## 検証

`admin/`で `pnpm test` / `pnpm typecheck` / `pnpm build`。
`server/`で `go test -race ./internal/presentation/handler ./internal/infrastructure/persistence/query/user`。
DBクエリテストには、migration 58まで適用した使い捨てDBの `ADMIN_TEST_DATABASE_URL` を指定する。作成したテストユーザーはトランザクションをrollbackする。migration 58のテストは独立した一時スキーマ内で実施し、共有DBのusersテーブルは変更しない。
