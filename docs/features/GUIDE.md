# 機能ドキュメント ガイドライン

## このガイドラインの目的

`docs/features/` 配下の機能ドキュメントについて、書く内容・書かない内容・書き方の指針を定める。

技術的な設計ドキュメント（実装方式・DBスキーマ・内部構造）は `docs/development/` 配下に置き、こことは役割を分ける。

---

## 機能ドキュメントの目的

機能ドキュメントは「この機能が何をするか」「どう動くか」の全体像を伝えるために書く。

- 読む人: 実装者、レビュワー、後から参加するメンバー、AI
- 伝えること: 機能の意図、ユーザー体験、ビジネスルール
- 伝えないこと: 実装の詳細（それはコードが正）

コードを読まなくても機能を理解できる内容だけを書く。実装方式や内部構造は範囲外。

機能ドキュメントは仕様の起点。仕様変更が発生したら、コードより先にドキュメントを更新する。

---

## 書く内容

### 概要

機能の目的と全体像を 1〜3 文で書く。

- この機能が誰の何を解決するか
- 機能の範囲（何をやって、何をやらないか）

### 用語

この機能に固有の用語を定義する。コード上の命名と紐づけることで、ドキュメント・コード・会話の用語を揃える。

- 全機能共通の用語（ユーザー、セッション等）は書かない
- コードの命名と日本語の対応が自明でないものを優先する
- 用語が少ない（2〜3個以下の）機能では省略してよい

### ユーザーフロー

ユーザー視点の操作手順を番号付きリストで書く。

- ユーザーの操作と、それに対するシステムの応答を交互に書く
- 正常系をメインに書き、主要な分岐（エラー、条件不足等）も含める
- 複数の独立したフローがある場合はサブセクションに分ける（例: 作成フロー、参加フロー、結果閲覧フロー）

### 呼び出しフロー

クライアントとサーバー間の呼び出しフローを mermaid で書く。

- ユーザーフローに対応するシーケンス図を書く
- 参加者はユーザー・クライアント・サーバーを基本とし、外部サービス（OAuthプロバイダー等）があれば追加する
- API のエンドポイント名を含めてよいが、リクエスト/レスポンスの詳細は書かない（それは API 仕様の役割）
- 1 つの図が大きくなりすぎたら、フローごとに分割する

### ルールと制約

ビジネスルール、計算ロジック、状態遷移、制約条件を書く。

#### 書く基準: 「何を守るか」

- 計算・判定ルール（例: 投票は1意見1ユーザー1回まで）
- 状態遷移（例: open → finished）
- データの制約（例: 同一ユーザーは同一セッションに二重参加しない）
- 参加・閲覧の条件（例: 属性制限を満たさないと投票できない）
- 条件分岐（例: 認証済みユーザーのみ作成可能）

#### 書かない基準: 「どう実現するか」

- ロック方式（SELECT FOR UPDATE 等）
- ログ出力の属性やストレージ設計
- 実装コード例（Go, SQL 等）
- インフラ・運用の設計

迷ったら「実装言語やフレームワークが変わっても残る情報か？」で判断する。残るならドメインロジック、残らないなら実装詳細。

> 既存ドキュメントには過去の経緯で実装詳細が含まれている場合がある。新規作成・改修のタイミングで順次この方針へ寄せる。

## 書かない内容

以下はそれぞれ Single Source of Truth が別にあるため、機能ドキュメントには書かない。

- API 仕様（エンドポイント、リクエスト/レスポンス、ステータスコード）→ TypeSpec（`tsp/`）
  - ただしシーケンス図内でエンドポイント名に触れるのは OK
- DB 仕様（テーブル定義、ER 図、インデックス設計）→ サーバーコード（マイグレーション・sqlc）
- 実装詳細（排他制御、ログ設計、キャッシュ戦略、インフラ構成）→ コードと `docs/development/`

---

## 関連機能の扱い

機能間に依存がある場合（例: トークセッションと参加アンケート）:

1. 各ドキュメントはそのユーザーフローの中で自己完結させる
2. 他機能の概念が出てきたら、フローを理解するのに最低限必要な説明だけ書く
3. 関連ドキュメントへの双方向リンクを張る

例: talk-session.md → `[参加アンケート](./talk-session-survey.md)` / talk-session-survey.md → `[トークセッション](./talk-session.md)`

---

## ファイル構成

- 基本は 1 機能 = 1 ファイル（`docs/features/{feature-name}.md`、kebab-case）
- サブドメインが独立したユーザーフローを持つ場合はディレクトリに分割
  - `index.md`（概要・用語・全体の状態遷移）を必ず置く
  - 各ファイルはサブドメイン単位で自己完結させる
- 分割の判断基準: そのサブドメインだけで独立したユーザーフローとドメインロジックがあるか
- mermaid を使うため、画像ファイルの管理は不要

---

## 作成・更新のタイミング

原則: 仕様変更が発生したら、機能ドキュメントから更新する。ドキュメントが仕様の起点であり、コードはそれに追従する。

- 新機能
  - 設計フェーズ: 機能ドキュメントを作成し、TypeSpec と同時に（または先に）PR でマージ
  - 実装中: 仕様変更があればドキュメントを先に更新し、実装 PR と一緒にマージ
- 外部連携など不確定要素がある場合
  - 仕様が判明したタイミングで作成・更新する
  - 「やってみてわかったこと」を反映し、後から参照する人が同じ調査をしなくて済むようにする
- 既存機能の変更
  - 仕様変更が発生したらドキュメントを先に更新してから実装に入る
  - 機能に変更を加える PR では、ドキュメントの更新が必要かを確認する
